Add Role-Based Access Control (RBAC) to the application. Today the User model has a single `is_superuser` boolean. That's not enough for a multi-stakeholder product. This feature introduces a proper Role + Permission system with middleware-level enforcement, admin-managed role assignment, and conditional UI.

Scope this as **Phase 1** (single sprint). Phase 2 (permission editor UI, custom role creation, audit log of role changes) is explicitly out of scope for this brief — deliver Phase 1 cleanly first.

## Requirements

### 1. Data model

- New `Permission` table: `id` (UUID), `name` (string, unique, e.g. `items.read`, `items.write`, `items.delete`, `users.admin`), `description` (string), `created_at`.
- New `Role` table: `id` (UUID), `name` (string, unique, e.g. `viewer`, `editor`, `admin`), `description`, `created_at`.
- New `RolePermission` link table (many-to-many).
- New `UserRole` link table (many-to-many; a user can hold multiple roles).
- The existing `is_superuser` flag is RETAINED and grants ALL permissions implicitly (no migration burden on existing data; do not migrate users to a role).
- An Alembic migration creates the four new tables AND seeds three baseline roles (`viewer`, `editor`, `admin`) with these permissions:
  - `viewer`: `items.read`, `users.read`
  - `editor`: `items.read`, `items.write`, `users.read`
  - `admin`: all of the above plus `items.delete`, `users.admin`

### 2. Backend middleware / dependency

- Add a FastAPI dependency factory `require_permission(perm_name: str)` that:
  - Resolves the authenticated user via the existing auth path (works for both JWT session AND API-key bearer auth from the previous sprint).
  - If `user.is_superuser`, allow.
  - Otherwise, gather all permissions across all roles the user holds; if `perm_name` is in that set, allow; else raise HTTP 403 with a structured error body (`{detail: "missing permission", required: <perm_name>}`).
- Apply `require_permission` to existing item routes:
  - GET routes → `items.read`
  - POST / PUT routes → `items.write`
  - DELETE route → `items.delete`
- The existing user-admin routes get `users.admin`.

### 3. Backend role-management endpoints (admin-only)

- `GET /api/v1/roles` — list all roles with their permissions; requires `users.admin`.
- `POST /api/v1/users/{user_id}/roles` `{role_id}` — assign a role to a user; requires `users.admin`.
- `DELETE /api/v1/users/{user_id}/roles/{role_id}` — revoke a role; requires `users.admin`.
- `GET /api/v1/users/{user_id}/roles` — list a user's roles; requires `users.read`.

### 4. Frontend (TanStack Router + Chakra)

- New admin-only route `/admin/users` (or extend the existing user-list page) — shows each user with their current roles as Chakra badges. A "Manage roles" button opens a modal with checkboxes for each available role; submitting calls the assign / revoke endpoints.
- Conditional UI gating elsewhere: hide the items-create button if the current user lacks `items.write`; hide the items-delete button if they lack `items.delete`. The current user's permission set should be fetched once at login and cached in app state (TanStack Query is fine).
- New `useHasPermission(perm: string)` hook in the frontend client to centralize the check.

### 5. Tests

- Backend pytest tests covering:
  - Role/permission CRUD via the new endpoints.
  - `require_permission` correctly allowing superuser; allowing role-bearer; denying user without role.
  - Existing items routes return 403 for users without the right permission and 200 for users with.
  - API-key auth path also respects RBAC (an API key inherits its user's roles).
- Playwright e2e covering:
  - Admin logs in → navigates to `/admin/users` → assigns "editor" role to a viewer-only user → logs out → that user logs in → can see create-item button → creates an item → logs back out.
  - Admin revokes "editor" role → that user logs in → does NOT see create-item button.

### 6. Migration safety

- The Alembic migration must be backward compatible: existing users keep their `is_superuser` flag untouched. The new tables are additive.
- Existing tests that rely on `is_superuser=True` users must continue to pass.

### 7. Patterns to match

- Follow the repo's existing SQLModel + repository + service + router layering (the way notifications and api-keys did it).
- Errors follow the existing `HTTPException` shape; do not introduce a new error envelope.
- The frontend hook follows the existing `useAuth` / `useCurrentUser` patterns.

## Acceptance

- Existing `is_superuser=True` users continue to have full access (no regression).
- A user assigned the `viewer` role can read items but gets 403 on create/update/delete.
- A user assigned the `editor` role can create/update items but gets 403 on delete.
- Admin can assign and revoke roles via the UI.
- The Playwright e2e described above passes.
- No existing test fails.

Scope-fence reminder: NO permission editor UI in this sprint; NO custom role creation; NO audit log of role changes — those are Phase 2.
